# app-factory-skill

アプリ量産ダッシュボードのパイプライン候補（低評価の競合アプリと、その低評価レビューの不満の内訳を分析した候補リスト）から次に作るアプリを選び、開発担当のAI（Claude等）に渡す「開発プロンプト」を作成するためのスキルです。

- 候補の選定： 需要の証明、不満の集中度、推定開発日数、シーズンから根拠つきで提案する
- プロンプト生成： 共通デフォルト（HIG準拠、課金の誠実さ、審査ガイドライン4.3への配慮、無料版制限の事前明示など）をすべて含んだ、そのまま貼れる開発プロンプトを作る
- デザイン監査： 生成したプロンプトを design-check-skill のチェックリストで監査し、抜けを直す

## できること／できないこと

できること：
- パイプライン候補からの次作の提案と選定
- 共通テンプレート＋候補固有の仕様で埋めた開発プロンプトの作成・保存・受け渡し
- 作成したプロンプトのデザイン抜け監査（design-check-skill併用時）
- 共通デフォルトを変更した際の、既存プロンプト向け差分の提示

できないこと：
- アプリ本体の実装（実装はプロンプトを受け取った開発担当AIの仕事です）
- ダッシュボードや候補CSVの書き換え（状態管理はダッシュボード側。このスキルは状態を進める案内まで）
- App Store審査の通過保証（ガイドラインへの配慮はプロンプトに含めますが、審査結果を保証するものではありません）
- 公開後の問い合わせ対応やレビュー返信の文面作成

## 使い方

1. スキル対応エージェント（Claude等）に、このリポジトリをスキルとして読み込ませる
2. 候補リスト（CSV）をエージェントが読める場所に置く（後述「前提条件」の形式）
3. 依頼する。例：
   - 「パイプラインから次のアプリを選んで」
   - 「No.○ のプロンプトを作って」
   - 「共通デフォルトに○○を追加して」
4. 生成物： プロンプトは指定した作業フォルダ配下の `<アプリのslug>/prompt.md` に保存され、ファイルとして渡されます。そのプロンプトを開発担当のAIに貼れば実装が始まります
5. プロンプトを渡した後は、ダッシュボード側で候補の状態を進めてください（候補→仕様→開発中…）。スキルはその案内をしますが、ダッシュボード自体は書き換えません

## 前提条件

- **候補リスト（CSV）**： 1行＝1候補で、少なくとも次の情報を持つCSV： 対象競合アプリ名、競合の評価とレビュー数、低評価レビューの不満内訳、差別化の切り口、推定開発日数、シーズン、市場、対応プラットフォーム（列名は手元の形式に合わせて読み替えます）
- **ダッシュボード相当のもの**： 候補の状態（候補・仕様・開発中・審査中・公開・保守・撤退）を管理する場所。GitHubリポジトリである必要はなく、スプレッドシートやカンバンでも構いません
- **開発担当のAI／エージェント**： 生成したプロンプトを渡して実装させる相手
- 具体例： 元の環境では kajisho5/app-factory-dashboard（候補61件のCSVと事業計画を持つリポジトリ）がダッシュボードにあたります

- `templates/prompt-template.md` — プロンプトの雛形（共通デフォルト＋アプリ固有部分の差し替え枠）
- `examples/` — 作成済みプロンプトの実例2本（後述）
- `LICENSE` — MIT License

## 自分の環境に合わせる箇所

- 候補CSVの置き場所と列名
- プロンプトの保存先フォルダ（SKILL.md の手順4）
- アイコン作成手段（fresnel を使う場合はその入手先。無い場合は任意のレイヤードアイコン作成手段）
- デザイン監査に使う design-check-skill の参照先（使わない場合は SKILL.md の手順3を省略可）
- 量産ペースと、状態管理で使う状態の呼び名
- 課金の基本形（ここでは広告なし・サブスクなし・買い切りを既定にしています。自社方針に合わせて変更可）

## 実例（examples/）

- `examples/seijitsu-qr-prompt.md` — 「誠実QRリーダー」（QR／バーコードリーダー）のプロンプト
- `examples/atena-print-prompt.md` — 「宛名印刷 はがき・封筒」のプロンプト

どちらも元の環境で実際に作成したプロンプトをそのまま収録しています。そのため、固有名詞やリポジトリ名（seijitsu-qr-reader、atena-print等）は具体名のまま残しています。自分の環境で使うときは、これらを粒度と書き方の基準として参照し、そのままコピーして使わないでください。

## よくある質問

**Q. このスキルがアプリを作ってくれるのですか？**
A. いいえ。作るのは「開発プロンプト」までです。実装は、そのプロンプトを渡した別のAI（または人間）が行います。

**Q. 候補リストはこの形式でないとダメですか？**
A. 列名は読み替えますが、「競合の評価・レビュー数・不満の内訳・切り口・推定開発日数・シーズン・市場・プラットフォーム」の情報自体がないと、選定の根拠が作れません。最低限この内容を含むリストを用意してください。

**Q. ダッシュボードがGitHubにない場合は？**
A. 問題ありません。スプレッドシートやカンバンでも、候補の状態が管理できればこのスキルは使えます。スキルはダッシュボードを書き換えず、状態を進めるよう案内するだけです。

**Q. なぜ「公開リポジトリで開始」にしているのですか？**
A. 元の運用の都合です（後日プライベートに変更する前提で、秘密情報をコミットしないことを徹底する設計）。社内完結の運用なら、最初からプライベートにしてもワークフローは変わりません。

**Q. 課金の基本形（買い切り）は変えられますか？**
A. 変えられます。ただしこのスキルは「切り口が課金への不満である候補」を扱う前提で、隠れたサブスクや誤認させる課金導線を禁止する項目を含んでいます。基本形を変える場合は、その禁止項目の扱いも併せて見直してください。
